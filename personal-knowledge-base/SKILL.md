# Personal Knowledge Base

当用户希望把资料整理成个人知识库笔记时，使用这个 Skill。

目标 Obsidian 知识库路径：

`/Users/hxc/Library/Mobile Documents/iCloud~md~obsidian/Documents/my-obsidian`

整理后的文件统一放到：

`/Users/hxc/Library/Mobile Documents/iCloud~md~obsidian/Documents/my-obsidian/raw`

## 输入内容

用户可能会提供以下任意内容：

- 原始文字、随手笔记、复制的文章、会议记录、聊天记录、需求说明、个人想法。
- 一个或多个本地文件，需要读取后整理。
- 一个主题加上一些零散上下文，需要整理成长期可复用的笔记。
- 类似“整理成我的知识库”“放进知识库”“归档到 Obsidian”“整理下这份资料”的请求。

## 输出结果

在 `raw` 目录下最合适的分类里创建一个 Markdown 文件。

整理后的笔记应该满足：

- 忠于原始材料，不编造事实。
- 面向未来检索来整理，而不是只做简单摘要。
- 默认使用清晰中文，除非用户要求其他语言。
- 简洁但完整，让用户以后不打开原始资料也能理解重点。
- 保存为 `.md` 文件，文件名使用容易理解的中文。

## 分类目录判断

写入文件前，先查看 `raw` 下已有目录。可以使用：

```bash
find "/Users/hxc/Library/Mobile Documents/iCloud~md~obsidian/Documents/my-obsidian/raw" -maxdepth 2 -type d | sort
```

优先选择最贴近的已有分类。当前常见分类包括：

- `stills`：stills 项目或代码库相关笔记。
- `stills/laravel`：stills 项目的 Laravel 后端实现笔记。
- `团队与规范`：团队流程、工程规范、协作约定、管理制度。
- `团队与规范/云实文档资料`：云实相关文档和内部参考资料。
- `工作安排`：排期、任务计划、工作分配、待办、里程碑。
- `工具与效率`：工具、工作流、效率方法、AI 使用、自动化、编辑器或命令行实践。
- `汇报`：汇报材料、阶段总结、状态更新、复盘材料。

如果没有合适分类，可以在 `raw` 下新建一个简短中文文件夹。文件夹名称要能表达主题。除非内容确实很杂且没有更好归类，否则不要轻易使用 `其他` 这种过宽泛的名字。

## 工作流程

1. 理解资料。
   - 读取用户提供的全部内容或引用文件。
   - 判断核心主题、资料类型，以及用户以后可能会怎么检索它。
   - 保留具体事实、命令、路径、日期、决策和行动项。

2. 选择存放位置。
   - 先查看 `raw` 下已有目录。
   - 选择最相关的文件夹。
   - 只有当放进现有分类会影响以后查找时，才新建文件夹。

3. 确定文件名。
   - 使用能说明内容的中文文件名。
   - 长期有效的知识笔记，优先使用 `主题.md`。
   - 会议记录、工作安排、汇报、带时间属性的内容，优先使用 `YYYY-MM-DD 主题.md`。
   - 避免在文件名中使用这些字符：`/`、`:`、`*`、`?`、`"`、`<`、`>`、`|`。
   - 如果文件名已存在，加上简短区分信息，例如 `-2`，或者使用更具体的主题名。

4. 写入笔记。
   - 使用 Markdown 标题组织内容。
   - 保持 Obsidian 中阅读友好。
   - 不要把整篇笔记包在代码块里。
   - 不要在笔记中写“我是如何整理的”这类过程说明。

5. 验证结果。
   - 确认文件已经保存到预期路径。
   - 简短告诉用户保存位置，以及为什么选择这个分类。

## 推荐笔记结构

如果资料适合，可以使用下面的结构：

```markdown
# 标题

## 摘要

[用 2-5 句话说明这份笔记的核心内容和用途。]

## 关键要点

- [要点 1]
- [要点 2]
- [要点 3]

## 详细内容

[按主题整理原始材料。保留重要背景、判断、步骤、示例、命令、路径、链接等。]

## 行动项

- [ ] [如果原文有明确待办，整理到这里]

## 相关信息

- 来源：[用户提供的来源、文件名或链接；没有则写“用户提供内容”]
- 整理时间：YYYY-MM-DD
```

如果某个部分没有实际内容，可以省略。技术笔记中，如果代码块和命令有助于以后复用，就保留下来。会议记录或工作安排中，优先整理决策、负责人、截止时间和下一步行动。

## 质量要求

- 不要编造缺失信息。遇到不清楚的内容，标记为“待确认”。
- 用户自己的路径、项目名、命令、字段名要原样保留。
- 优先做结构化整理，不要只写一大段流水账。
- 对检索有价值的原始术语要保留。
- 如果资料包含隐私或敏感内容，只在本地处理，不发送到外部服务。
- 如果用户说“整理完直接放进去”，要实际写入文件，不要只展示草稿。

## 什么时候需要追问

只有在以下情况才简短追问：

- 用户没有提供资料，或者引用的文件无法访问。
- 多个分类都很合理，而且不同分类会影响以后查找。
- 用户要求了特定风格，但这个要求和内容或存放位置冲突。

其他情况下，直接做合理判断并完成整理。
